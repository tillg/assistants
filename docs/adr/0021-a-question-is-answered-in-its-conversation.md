# A question is answered in its Conversation

There were two menu entries for one act. *Open Questions* listed every question nobody had answered — a prompt and an `assistantKey` — and *Conversations* listed the runs that raised them; the User's actual job, *"look at what the household's assistants are doing and unblock the ones that are stuck"*, was split across both. The sharpest case is the approval [ADR-0018](0018-an-operation-may-require-an-approval.md) demands: one sentence about money, while everything that justifies it — the invoice the Receptionist classified, the accounts the Accountant listed, the budget report it read, the question it asked first and the answer it got — sits in `entries[]` on another document, joined only by a ThingID the User has to copy. Two answers are needed per booking, and both were given blind.

So the two lists become one. **`OpenQuestionModule` loses its `menu`, Conversations becomes the landing page, and a Conversation waiting on the User is marked 🛑 in that overview.** An open question is always the end of a Conversation, so a list of Conversations is already a list of questions — sorted by the thing they are about rather than by the fact that they are questions. The Conversation's own form stops rendering `entries[]` as a thirteen-column grid and renders it as a thread, under a header that does not scroll away, ending in the pending question with an **Answer** button.

**The answer is still written on the question's own form.** This is the part worth recording, because the tempting design is one screen: put the answer controls inside the Pending Question Bubble and write `OpenQuestion` from there. It was rejected. The form engine already validates an answer from `OpenQuestion_FM`, already guards it with `withDirtyHandling`, already renders the control each `kind` needs, and is already watched end to end. Answering in the Transcript would hand-write all four, bypass a Model's own form in the face of [ADR-0008](0008-every-data-model-has-a-form-model.md), and — the real cost — create a **second writer** for one fact, which is the failure [ADR-0006](0006-one-authority-per-fact.md) exists to prevent. The rule that falls out of it generalises: **reads may cross documents, writes may not.** The Conversation's form reads the pending question, the question's form reads its Conversation, and neither writes the other.

The price is one extra click, and an Answer Surface that shows a transcript the User was just looking at. That is deliberate rather than tolerated: it is the *same* component, so the second screen reads as the same thread continuing rather than as a different view of the same data. The Conversations list stays beside it as the master, so *Cancel* returns there and the 🛑 clears in a list already on screen.

## Considered options

- **Answering inside the Transcript.** One screen instead of two, and rejected above: hand-written validation, hand-written dirty handling, kind-specific controls duplicated in React, a Model whose form is bypassed, the existing end-to-end coverage of answering invalidated, and a new write path to the ThingStore. Every one of those is a thing the form engine already does correctly.
- **Keeping both menu entries and only adding the transcript.** Free, and it leaves the split inbox in place — which is half of what this change is about. A question would still be reachable without the reasoning that produced it.
- **Deleting `OpenQuestion_OM` and `OpenQuestionPending_QeM` along with the menu entry.** Tidier, and refused: an Assistant that can say *"here is the list of open questions"* would need an overview scene to put the User in front of. No such Operation exists and this change does not add one; what it does is decline to delete what one would need. The consequence is stated rather than hidden — until then those three models are read by nobody.
- **A `Blocked` boolean on `Conversation_DM` instead of an expression column.** Cheaper to render and a second copy of what `waitingFor` already says, written by the same writer in the same write. ADR-0006's whole subject. Derivation costs one expression in one model file.
- **`masterModule: "OpenQuestion"` for the Answer jump.** It would have given the dormant overview a reader for free, by rendering it as the master pane beside the question form. Refused because landing the User on a list of *questions* after answering rebuilds the second inbox this change exists to remove. It is a one-argument change in `openForeignForm` if those models ever need one.

## Consequences

- **The menu has nine entries and `OpenQuestion` is not one of them.** It was eight when this was decided; [ADR-0022](0022-a-dashboard-counts-it-does-not-keep.md) added the Dashboard and took the landing page with it, so the sentence above about Conversations becoming the landing page no longer holds either — what survives is the part this ADR is about. Its form is still a scene, still addressable by descriptor, still the Authority for an answer — it is simply not advertised. Deep links are off in this application (`deepLinking.onlyWelcomePage`), so reachability was never a URL and is not one now.
- **Cross-module navigation becomes something this client does.** The **Answer** button and the header's *about* link both leave their module, which needs a teardown-then-push saga rather than the row-click the platform ships: `crud-core`'s `selectRow` spreads the current descriptor and can never change module. Three traps are now specified rather than rediscovered — `model` is mandatory, `instance` is a composed `<Model>/<ThingID>` docRef and not the bare ThingID a Thing carries ([ADR-0002](0002-thingid-identifies-only.md)), and the cancel handshake is obligatory or activities leak and the layout breaks.
- **No menu entry highlights while the Answer Surface is open**, because `OpenQuestion` no longer has one to deep-equal against. Accepted.
- **`Conversation_FM`'s thirteen-Control header section becomes collapsible and starts collapsed.** ADR-0008 is still met — every field is still on the form — but they are one click away, because they are for debugging a Conversation and the pinned header is for reading one. `OpenQuestion_FM`'s `SectionQuestion` splits the same way: the prompt stays open, its four machinery Controls move into a collapsed *Details* section.
- **The token figure becomes visible to the User, and it is rendered `≥`.** `recordUsage` stamps a Turn's usage onto the first Entry that Turn wrote, and a Turn that threw before writing one records nothing — so the sum is a lower bound, and the first place that claim reaches a human says so.
- **Nothing about the Runtime, the write model, the Models' data or the roles changes.** No new field, no reindex, no migration. `waitingFor` was already indexed and already said everything the 🛑 needs.
