# A Dashboard counts; it does not keep

The application opened on the Conversations overview — a table of every Conversation there has ever been, `done` and `failed` alongside the three that need something. [ADR-0021](0021-a-question-is-answered-in-its-conversation.md) made that table the single inbox and marked the blocked rows 🛑, which was the right fix for a table. It is still a table, and a table is what you read second. What a User wants on arriving is the shape of the household's admin in one look: is anything stuck, is anything arriving, is anything running. So the landing page becomes a **Dashboard** — first in `modules[]`, therefore first in the menu, four **Tiles**, each a summary of one part of the admin and a door to the module that holds it.

The moment a screen exists whose entire job is to show numbers, the question is where the numbers live, and it has exactly one tempting wrong answer: put them somewhere. A `documentCount` on `RuntimeState`, incremented by the watcher; a nightly aggregate Thing; a figure held in the client between visits. Each of those is cheap on the day it is written and each of them is a **second Authority for a fact the ThingStore already owns**, which is the failure [ADR-0006](0006-one-authority-per-fact.md) exists to prevent. A count is not a fact anyone may keep. It is the store's answer to a question that was asked.

**So: every number on the Dashboard is a `fullSize` from a query against the Authority that owns the fact, read on mount, and never cached, polled or aggregated into a Thing.** `useThingCounts` batches a Tile's counts into one `Dispatcher.rpc` call, reads `fullSize` off each response and discards `entries` — which is the invariant that makes the hook safe to point at any Model, because nothing it returns can become a second copy of a Thing. Three of the four questions were already indexed facts nobody was asking: `Conversation.Status`, `Conversation.WaitingFor` and `Document.CreatedAt` all carry `indexed` because the Trigger Watcher needs them, so this change adds no Model, no field and no index. The Assistants Tile is the one exception and it proves the rule rather than bending it — a name is not a count, so it reads one page of Assistant documents — twenty-five at most — and lifts three fields off each, and the rest of the body, `SystemPrompt` and every Skill's markdown, is discarded rather than held.

**And where a fact's Authority cannot be reached from the browser, the Tile is a link and shows no number rather than showing one somebody else computed.** That is the books, and it is the sharpest illustration of ADR-0006 in the application. Bookkeeping is the Authority for accounts, balances and transactions and nothing here holds a second copy — deliberately, down to the Invoice having no `paid` field. Firefly III publishes no port; every browser request goes through `firefly-proxy`, which runs its own OIDC flow, and the web application holds a Keycloak token for the ThingStore and nothing Firefly would accept. The one component holding Firefly's personal access token is the Runtime, and the Runtime offers no API and receives no calls ([ADR-0011](0011-the-runtime-polls-the-thingstore.md)). A balance on that Tile therefore requires the Runtime to grow an API, or a Firefly credential to reach the browser, or this system to cache a foreign fact — three things the architecture already says no to, for one figure. The Tile is a door, it says so, and it is the only one with no **Headline**: a Tile that has no honest number shows none.

This is recorded rather than left in the change's specs because it will be re-litigated the first time a Tile is slow, and the answer then is not a cache.

## Consequences

- **The numbers are as old as the moment they were read, and each Tile says so.** Nothing polls — the store already carries the Runtime's two-second scan, and a Dashboard polling beside it would be standing query load for a screen nobody is watching; the platform offers no subscription either. So every Tile that queries renders an `as of 14:32` footer from its own read instant, and leaving the Dashboard and returning re-reads everything. A stale number that admits its age is honest; a live-looking one is not.
- **The createdOn lag is visible, and it is meant to be.** `Document.createdAt` is the **Runtime's** field, backfilled at the start of a scan, because A12's form engine offers no save hook that could stamp one. A Document created in the web application while the Runtime is paused counts in the unconstrained Headline and in no month's bucket, so the **createdOn curve**'s last point can sit below the Headline. Naming the gap makes it a fact; the alternative — dropping the Headline and reading the curve's last point as the total — would replace a visible discrepancy with a quiet undercount.
- **The Documents Tile costs fourteen queries per visit, and each one drags back a document.** `paging.pageSize: 0` is rejected by the store, so `PAGE_SIZE` is 1 and every count also returns one body. Measured against the demo household: the Documents Tile's fourteen counts weigh ~3.6 kB over 49 Documents, the Conversations Tile's three weigh ~12 kB because a Conversation carries its transcript. Kilobytes, once per visit, one round trip per Tile — and the price of not holding a single number anywhere.
- **A count field on a Thing is refused, and so is the batch that would fill it.** `RuntimeState.documentCount` drifts the first time anything is deleted outside a scan, and it puts a write on the Runtime's critical path for a number that exists only to be looked at.
- **Server-side aggregation is not rejected, it is unavailable.** `dataservices-access`' `Query.AggregationProjector`, `ProjectionField` and `AggregationFunction` each carry `@important This feature is not supported yet`; one grouped `count` query would be a query the server refuses. Thirteen cheap `date_range` counts over an existing index are what the curve is built from instead. When the platform ships aggregation, the createdOn curve is the first place worth spending it.
- **A Query Model per count is refused.** A `_QeM` is a *stored, named* query, right for something more than one client needs, as `OpenQuestionPending_QeM` is. Thirteen of these are date windows relative to today: thirteen models that would change meaning every month.
- **Counting in the client is refused twice over.** `useThingById` per row fetches every document in order to count them, when the store already knows; and a saga with a redux slice would buy a channel, an action and a reducer for a read that nothing else consumes. `Dispatcher.rpc` is a promise API over the `ServerConnector` singleton and that is all this needs.
- **The Dashboard is placed in the model, not in React.** A Content Model rendered by the Content Engine would still need a custom content element per Tile, because every number on the page is dynamic; a `CustomScreenElement` needs a document to hang off, and inventing a Dashboard Thing to give a screen somewhere to live is a Model created for the UI's convenience. One view holding four tiles in React would work and would put *what is on the Dashboard* in code. The four `VIEW_ADD`s cost four adjacent directives in `AssistantsAppModel_AM.json` and four `addView` lines in `appsetup.ts`, and buy per-Tile error boundaries the platform draws for free: one Tile that throws leaves the other three standing.
- **No decoration got a Model change.** An `Icon` field on `Assistant_DM` is a model change, a form change, a bootstrap reconciliation decision and a migration, for an emoji. Every Assistant is the 🤖 the icon vocabulary already has.
- **Nothing about the Runtime, the write model, the Models or the roles changes.** The Runtime does not know the Dashboard exists, the ThingStore is still the only integration surface, and this change is one more reader of it. The model count is unchanged at twenty-nine.
