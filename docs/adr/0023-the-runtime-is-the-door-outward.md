# The Runtime is the door outward

Every External System this application talks to is reached through a Connector in the Runtime. Every foreign credential — Firefly's personal access token, the LLM provider's key — lives in that one process, and translation between a Thing and a foreign representation is defined to happen there and nowhere else. That was easy to hold while the only caller was an Assistant, because an Assistant *is* the Runtime running a Turn. It stopped being easy the moment the [Dashboard](0022-a-dashboard-counts-it-does-not-keep.md) wanted a balance on it: the browser holds a Keycloak token for the ThingStore and nothing Firefly would accept, and the question *"what do the books say?"* has exactly one component in the system that can answer it.

**So the Runtime accepts one kind of inbound call: execute a named Operation and return its result.** Four conditions, `and`ed, never `or`ed — the Operation is on a deployment allowlist in configuration, its Implementation declares `clientReadable` in code, its Implementation is `mutating: false` in code, and its Operation Thing is not switched off. The server checks its own allowlist before it forwards, and that is the whole of the outer gate — it narrows *which names* reach this door and nothing more. `Enabled` is read in the Runtime, by the inbox itself (`runtime/src/inbound/server.ts`), beside the four `and`ed checks its `gate.ts` (sixty lines, pure, no I/O) makes before anything executes, because the refusal that matters must happen in the process that would do the executing. Nothing on that path stores an answer: no Thing, no cache, no copy held in the server, nothing in `sessionStorage`. When the call is over the system holds exactly what it held before. **Foreign data is routed, not copied.**

This amends [ADR-0011](0011-the-runtime-polls-the-thingstore.md), which refused the Runtime an API, and the amendment is narrower than it looks. Read what ADR-0011 actually argues: the ThingStore is the Authority for Conversations and Open Questions, so *"is there anything to do?"* is a question about the store and nothing else is entitled to answer it — and an API would hold in memory a pending request, a subscription or a callback, which is exactly the durable live state [ADR-0004](0004-assistants-suspend-and-resume.md) exists to remove. A synchronous read of a foreign system is neither of those things. It carries no pending work, it creates no waiting state on either side, and it is over before the next scan. Everything about pending work still goes through the store, the Runtime still polls every two seconds for all of it, and there is still no second place to ask what is waiting. The sentence at the top of `index.ts` — *"There is nothing else. No HTTP server, no queue, no scheduler"* — is narrowed rather than withdrawn, and it is narrowed in that file in those words.

The alternative that looks cheaper and is not is **storing the answer as a Thing**. A `BookkeepingSnapshot`, refreshed by the Runtime and read by the client like any other Thing, keeps every boundary this system has and needs no new call path anywhere; it was the obvious design until you say out loud what it does. It copies the household's bank balances and transaction history into the ThingStore's Postgres, and therefore into its backups, its exports, its overviews and its write-ahead log, where nothing reads them. That refusal is on **data minimisation, not on Authority** — a dated snapshot answers [ADR-0006](0006-one-authority-per-fact.md) honestly enough, and is still a duplicate of the most sensitive data in the system held in the one place with no use for it. Routing keeps the Authority claim true by construction rather than by discipline: there is nowhere for a stale copy to live.

Two other routes were refused. **The server holding the Firefly credential** would make the smart store — three hand-written Java classes, none of them domain-aware — the first component that is both a store and an integration, and it would need doing again for the bank and again for email. **The browser calling `firefly-proxy` directly** is not a judgement but a measurement: `GET firefly:8080/api/v1/accounts` with `X-Forwarded-Email` and no token answers `401 {"message":"Unauthenticated."}`. `remote_user_guard` guards Firefly's *web UI*; its API wants a personal access token, which is the one thing the browser must never be given. A dead end, tested rather than assumed.

The property the whole decision hangs on, stated once: **opening a read route does not open a write one.** It was verified against the live stack from the browser's own position — an allowlisted read answered, `bookkeeping.postTransaction` was refused, a non-mutating Operation that is not on the allowlist was refused, a call with no bearer token was a 401, and Firefly held twenty-four transactions before the attempt and twenty-four after.

## Consequences

- **`requiresApproval` does not protect this route, and nothing about that is obvious.** Approval is enforced in the Turn loop — `LoopDriver.gateOnApproval`, `advance.ts:760` — not inside an Implementation. Calling `execute()` directly walks straight past it, along with `grantedTo()`, the intent log and the idempotency-key convention; `runtime/test/operations.test.ts:303` already books a transaction exactly that way. So the refusal of anything `mutating` is the *whole* guarantee, and it is not backstopped by the approval flag: widening the allowlist to a mutating Operation would not be saved by its requiring an approval, because the approval layer is not on this path at all. The gate refuses on the seed's `requiresApproval` as well, but only as belt-and-braces with `mutating`, and only because it is the one place the inbox can see that an Operation shipped wanting one.
- **`Mutating` is never read from the Thing for this decision.** `registry.ts` had already refused to trust it and says why: `reconcile()` treats a non-mutating Operation as safe to consider repeated, so a `mutating: false` edited onto a booking would make crash recovery report it as harmless — [ADR-0012](0012-a-conversation-is-an-intent-log.md)'s failure, supplied by the safety mechanism. The same reasoning applies with more force where the caller is a browser. Code is authoritative and the Thing is not, which inverts the elegant story that the catalogue governs everything: `Enabled` is the User's decision and is read from the Thing; `Mutating` is a claim about code and is read from code. `clientReadable` follows the same rule and for the same reason — it lives on the Implementation, next to the author who knows whether it holds.
- **The allowlist is a separate control and is not redundant with `mutating`.** `mutating: false` means *changes nothing*; it does not mean *safe for a browser to invoke at will*. An LLM-touching Operation is non-mutating and costs money every time it is called. The allowlist ships with exactly the two Operations the Dashboard names, and widening it is a decision taken each time rather than a consequence of marking something non-mutating.
- **The Dashboard now depends on the Runtime being up.** There is one replica ([ADR-0014](0014-exactly-one-runtime-replica.md)) running a two-second scan loop, so a wedged or stopped Runtime takes two Tiles with it while the other four still render. That is the honest rendering: *"the door outward is shut"* is the correct answer to *"what do the books say?"* when the only component that can ask is down, and it is better than a number from a cache that would have been wrong in a way nobody could see. The store's own unavailability is treated the same way — the `Enabled` check fails closed, because a check that grants access must never read *"I could not find out"* as *"go ahead"*.
- **A refusal says `not-allowed` and says no more.** Unknown, disallowed, mutating, approval-guarded and switched-off are one outward answer, so a browser probing the route learns nothing about which Operations exist. An unauthenticated caller is refused before the gate is consulted at all, and a failure of the External System is a 502 rather than a 403 — *"Firefly is down"* and *"you may not ask that"* are never the same line in a log.
- **The transport is `node:http` and no framework.** One route and a JSON body is twenty lines of standard library, and adding Express to a process whose job is a scan loop would be a dependency, a lockfile change and a supply-chain surface for something that needs none. The listener is closed explicitly on SIGTERM: an open listener keeps the event loop alive, and without that the container would stop responding to its own shutdown signal. It publishes no host port — it is reachable only from inside the compose network, behind a shared secret compared with `timingSafeEqual`, and the boundary that faces the world stays Keycloak at the server.
- **This is the shape the system grows into, and it is built once.** The two rejected designs would each need repeating per external system; this one does not. A new read Operation becomes callable from the UI on the day it is written and its key is allowlisted — no server change, no Model, no endpoint. What it must never become is a general proxy of arbitrary Operations to arbitrary callers, and the four checks exist precisely so that it is not that.
