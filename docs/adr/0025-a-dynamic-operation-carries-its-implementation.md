# A Dynamic Operation carries its Implementation

[ADR-0019](0019-an-operation-is-a-thing.md) moved the catalogue of Operations into the ThingStore so a User deciding what the Receptionist may reach would not have to read TypeScript. It half-worked. They can read what an Operation *claims* to do, guard it, weaken it and switch it off — and if they want to know what it *does*, they are back in `runtime/src/operations/implementations.ts`. For `thingstore.create` that split is honest: the answer really is *"it writes a Thing here, in this system's own terms"*, and that Implementation knows about `ThingRepository`, about idempotency keys, about the Conversation it runs inside. For `bookkeeping.listOpenItems` the answer is *"it calls `GET /api/v1/accounts` and keeps the non-zero payables"* — four lines the User could read, and today cannot, because they are compiled into the process that watches the mailbox.

So the catalogue splits in two. A **built-in** Operation runs inside this system's own scope, context and domain — it reads and writes Things, asks the User a question, starts an Assistant, reads bytes out of the Content Store — and its Implementation stays compiled into the Runtime, exactly as ADR-0019 left it. A **dynamic** Operation is the other case: a foreign HTTP API reached with a credential, whose answer has to be turned into something a model can read. Its Implementation is **carried by its own Operation Thing**, as TypeScript source the User may read and edit, and executed by a new **Operation Host** rather than called. All seven `bookkeeping.*` Operations become dynamic; nothing else does. An Assistant cannot tell which kind it is holding, and that is the acceptance criterion.

**All of it runs server side.** The source is stored in the ThingStore, compiled in the Runtime container and executed in a worker thread inside that same process. The browser never receives it, never evaluates it and never learns it exists. The one inbound route ([ADR-0023](0023-the-runtime-is-the-door-outward.md)) still names an Operation and gets a value back, and that the value was produced by stored source rather than compiled source is invisible from outside the container.

## The sentence this amends

ADR-0019 says, in the words this decision is obliged to quote rather than paraphrase:

> **The Implementation cannot be data, and that is what makes this safe to do.**

This decision makes it data, for half the catalogue. That is a real amendment and it is stated here in the terms of the thing it weakens.

**But the protection ADR-0019 named never came from the code being compiled.** The paragraph that follows the quoted sentence says what it was protecting against: *"`exec` with extra steps"* — an Assistant talking its way into arbitrary code execution, which is learning 17 of [ASSISTANTS_VS_OPENCLAW.md](../../specs/research/ASSISTANTS_VS_OPENCLAW.md). That protection was **write authority**, not the compiler, and it survives this change intact. An Assistant cannot author a dynamic Operation, for four store-side reasons, each already true:

1. The `runtime` role holds no `ASSISTANT_WRITE`, and the authorization policy withholds `Operation_DM` from anyone without it ([D-007a](../../DECISIONS.md)).
2. `Operation_DM` is absent from `WRITABLE_MODELS`, so `thingstore.update` refuses it with a message the model can read.
3. It is absent from `READABLE_MODELS`, so an Assistant cannot read the source that would constrain it.
4. It is absent from `TRIGGER_ELIGIBLE_MODELS`, so an edit to a stored Implementation cannot give birth to a Conversation.

The only actor who can write a dynamic Operation's source is the human being who could already `git push` to this repository, and who could already rewrite an Assistant's system prompt — the more dangerous of the two, and one that has been data since [ADR-0003](0003-assistants-are-things.md).

## What genuinely weakens

Two things, and they are narrower than the amendment sounds.

**`mutating` and `clientReadable` come from the Thing for a dynamic Operation.** `registry.ts` reads `mutating` from code and refuses to read it from the Thing, for an exact reason: `reconcile()` treats a non-mutating Operation as safe to consider repeated, so a `mutating: false` edited onto a booking would make crash recovery report a double posting as harmless. For a built-in that is unchanged. For a dynamic one there is no compiled author to ask, so both flags become fields on the Thing, and the trust anchor moves from *code review* to *store write authority* — which the four facts above make genuinely narrow.

**The deployment allowlist carries the inbound gate.** `gate.ts`'s four checks are the deployment allowlist (`config.clientCallable`, from the compose file), `clientReadable`, `mutating: false`, and no approval requirement. For a built-in the last three come from code; for a dynamic one they come from the Thing. The allowlist — which lives in the compose file and not in the store — is therefore what stands between a mis-edited flag and a browser, and it becomes the strongest of the four. This is the one place in the change where a User's edit could open something a code review used to close, and it is named here rather than implied.

**The sandbox is containment, not a security boundary — in those words.** The Operation Host runs source in a `node:vm` context with a curated global object, inside a worker thread with no module loader, a hard timeout and a memory ceiling. It stops an *honest mistake* — an infinite loop, a runaway allocation, an accidental reach for `fs` — from taking down the scan loop. It does **not** stop a determined attacker who can already write to the store, and it is not claimed to. The boundary that keeps an Assistant out of this is the store's write authority; the sandbox's job is smaller and is stated as smaller.

## Considered and rejected

- **Mounted config files instead of source on the Thing.** The Implementation would live in a file mounted into the container. Refused for ADR-0019's own reason for putting the catalogue in the store: the User cannot edit a file inside a container. Source on the Thing is versioned by the store, readable in the web application beside the prose that describes it, and editable by exactly the actor already trusted with Assistant prompts.
- **Hybrid file-seeded source.** Seed the source from a file, then let it be edited in the store. This is what bootstrap does — the seed carries the source, and `source` is on the *decision* side of bootstrap's line, created once and never re-applied — but the *authority* is the Thing, not the file. A running Operation's source is never overwritten by `just dev`; divergence is reported by name, exactly as `description` already is.
- **`node:vm` alone.** A `vm` context has curated globals but `await` escapes its `timeout`, and it has no memory ceiling. A worker alone has a hard `terminate()` and `resourceLimits` but the full Node surface. Neither alone is enough; the Host uses both. Neither, and not both, stops an attacker who can write the store — the boundary is elsewhere.
- **A child process per call.** Heavier than a worker for the same containment, and it still would not be a security boundary against a store-writer. A worker spawn is 15–30 ms against 50–300 ms of HTTP; a worker *pool* was rejected in turn, because a pool means residual state between two Operations' executions and that is harder to reason about than 30 ms.
- **Precedence instead of ambiguity.** A key that resolves to *both* a compiled and a stored Implementation could be ranked — code wins, or the Thing wins. Refused: it is the wrong shape. A `bookkeeping.postTransaction` in both places means somebody is mid-migration and does not know which one just moved money. [ADR-0006](0006-one-authority-per-fact.md)'s *one authority per fact* applies to *"what does this Operation do"* with more force than to anything else in the catalogue, so the grant is **dropped as ambiguous**, not resolved.
- **A compiled shim per External System.** Keep `FireflyConnector` and let source call `host.firefly.listAccounts()`. It would make the migration trivial and defeat the point: the 707 lines would still be compiled in, the *n*th system would still need its own module, and the User reading `bookkeeping.getBalance` would find a method call into code they cannot see. The value of the change is that the source shows the HTTP.

## Consequences

- **The User can, for the first time, create a capability rather than only constrain one.** Every other Operation is granted, approved, reconciled and refused by the User; a dynamic one is all of that *plus* written by them. It is safe to say because the actor who can write an Operation Thing is already the actor who can rewrite an Assistant's system prompt.
- **Integration churn stops being a release.** Firefly answers `liabilities` where its write API accepts `liability`; that mismatch made `listOpenItems` report nothing while thousands were owed (BUG-02), and fixing it meant a rebuild and a redeploy of the process that watches the mailbox. The blast radius of a spelling fix in a foreign API's vocabulary is now that Operation and no more, and the spelling is on the page where a reader can see it.
- **`DroppedGrant["reason"]` gains `"ambiguous"` and `"uncompilable"`, and both reach the model.** ADR-0019's reason for saying `disabled` out loud applies: *"X is not one of your tools"* is a false premise a model re-plans around, and *"that Operation's stored code does not compile"* is one the User can act on.
- **A dynamic Operation that is `mutating` and declares no `reconcile` is reported, not refused.** The loop already escalates to the User rather than guessing, which is the safe answer; but `bookkeeping.postTransaction` without a `reconcile` is a double booking waiting for a crash, so it is named at bootstrap and at resolution.
- **The `postsInFlight` single-flight map is a deliberate loss.** `FireflyConnector` held an in-process map that collapsed two concurrent posts of the same transaction into one. It is gone with the class, and its job is covered by `external_id` idempotency plus the single Runtime replica. Recorded as a loss rather than a port.
- **The switch is an offline migration, and rollback is not code-only.** `import/migrations/2026-08-19-bookkeeping-operations-dynamic.sql` sets `implementation`, `source`, `egress`, `clientReadable` and `mutating` on the seven existing Things. It must run in the same maintenance window as the image swap, with the Runtime down: a migrated Thing meeting the still-compiled code drops as `ambiguous`, and the new image meeting an un-migrated Thing drops as `unimplemented`. Restoring the previous image while the Things still read `implementation: dynamic` drops all seven as `ambiguous`, so rollback restores the old image **and** reverts the Thing fields in the same offline window. `mutating` and `clientReadable` are set by the migration because the registry and gate begin reading them off the Thing, and the values the Things carried from their built-in days were never authoritative.
- **`FireflyConnector` keeps `isReachable()` and loses the rest.** The word *Connector* survives for Mail, the Content Store and the Manual Connectors; for Bookkeeping the Connector has become the Operation Host plus the source it runs. Its integration tests are re-pointed at the dynamic Operations through the Host — the same assertions, one layer out, against the same live Firefly — rather than deleted.
