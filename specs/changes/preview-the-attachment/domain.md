# Domain — nothing, and that is the finding

No new terms. No new Things. No new states, no new Operations, no change to any Authority, and
nothing an Assistant can see.

That is worth an artifact rather than an empty file, because a change that touches the domain nowhere
is a change whose scope can be argued about cheaply — and because two of the words nearby are close
enough to be reached for by mistake.

## Why there is nothing to add

The bytes already have a place in the language. A `Document` is *the item itself together with
whatever text was extracted from it*, and its attachment is a field group on it — modelled since the
beginning, `repeatability: 1`, holding `attachment_id`, `mime_type`, `original_filename` and the rest.
Rendering that group is a **presentation** decision, and presentation is what a `FormModel` is for:

> **FormModel**: The A12 form model through which a Thing is presented and edited. Every Model has
> one: generated by default when the Model is created, and freely modifiable afterwards.

So the honest description of this change is *"the FormModel presents the attachment differently"*. The
only reason it needs code rather than a model edit is that A12's form engine previews images and not
PDFs — a limitation of the platform, not a gap in the domain.

## The two words not to reach for

**Not a Skill.** The temptation is smaller here than it was for the readers, but the rule is the same
one and worth restating because it keeps being the test: a Skill is *instructions for the LLM*. No LLM
is involved in this change at any point. The preview exists for the **User**, and the User is not an
Assistant.

**Not an Operation.** An Operation is *a capability one System offers* — and it is offered **to
Assistants**. Fetching bytes so a browser can draw them is not a capability any Assistant needs, must
not be reachable by one, and would be the first entry in the catalogue that existed for the benefit of
a human rather than an actor in the system. The `UserInterface` is an Internal System through which
*Assistants show Things to the User*; this is the User looking at a Thing directly, which needs no
System at all.

If a future change wants an Assistant to *see* an attachment — a vision model reading a scan is the
obvious one — that is `document.readScan`, it already exists, and it is deliberately on the other side
of this line: it spends money and it writes a field.

## What the change does touch, in domain terms

One sentence, and it is about supervision rather than about data:

> **The User is the human the system works for, and the supervisor of every Assistant's activity.**

The Receptionist writes a `classificationNote` explaining what it decided and why —
*"Always record your reasoning, even when it is obvious — the User reads this."* Checking that
reasoning against the document it was about is the whole of supervision here, and until now it
required leaving the application. A preview does not add a domain concept; it removes an obstacle to
one that was already there and not being exercised.

## A distinction this change makes visible

The letterbox created a category the domain had not needed a word for and still does not: **a Document
that is not about anything**. A letterhead logo and a *Widerrufsbelehrung* arrive as Documents because
they arrive as attachments, and the Receptionist classifies them `other`.

They are still Documents by the definition — *anything that has arrived but has not yet been
understood* — and they were understood, correctly, as not mattering. So no new term is needed. But it
is the reason a preview earns its place: three Documents from one mail, two of them noise, and the
cheapest possible way to confirm which is which is to look.
